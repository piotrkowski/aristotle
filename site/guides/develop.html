Develop

Most work needs no Kindle: every screen renders to PNG on the host, pixel for pixel what the panel gets. The emulator and the device come after.

Two workspaces

The root workspace holds the pure-Rust crates (the hardware layer, the UI toolkit, the library, the measurement tools) and builds anywhere with cargo test. The native workspace, the renderer and the reader app, links Plato's engine and its C libraries, which tools/build-plato.sh builds once with Zig. Keep builds under $ARISTOTLE_CACHE/ and point CARGO_TARGET_DIR and TMPDIR there.

cargo test                                     # root workspace

# native workspace on the host: C libraries once, about 6 minutes on 2 cores
PLATO_TARGET=x86_64-unknown-linux-musl PLATO_LIBS_ONLY=1 tools/build-plato.sh
CARGO_CMD=test tools/build-render.sh host

Previews on the host

Two previews drive the same code the device runs, with simulated touches, and write one PNG per step:

# every screen of the toolkit, day and night
cargo run --release -p aristotle-ui --bin aristotle-ui-preview

# the reading interactions on a test book: menu, contents,
# dictionaries, selection, highlights, footnotes, "go to"
devloop/host/make-reading-test-epub.py BOOKS/Aristotle/proba-czytania.epub
$ARISTOTLE_CACHE/render/host/aristotle --data DATA --library LIB \
    --dict DICTIONARIES --preview OUT BOOKS/Aristotle/proba-czytania.epub

Both report every panel update with its waveform and rectangle (the reader in updates.txt). Compare them before and after a change: the images should stay identical unless the change is about how things look.

The emulator

devloop/emulator/setup.sh builds a QEMU Paperwhite 4 running the stock firmware 5.13.6, with KUAL, MRPI and the jailbreak. Anything that could hang boot, touch the stock framework or load kernel code goes there first. It does not reproduce e-ink timing or ghosting; that needs the device.

devloop/emulator/setup.sh
cd $ARISTOTLE_CACHE/emulator/eink-emulator
./eink run pw4 --headless --qmp-socket --serial-socket

Scenarios on the device

aristotle-observe runs touch scenarios from devloop/kindle/scenarios/ against the stock interface or Aristotle. It reads the panel driver's own log and reports, per interaction, the time to the first and last update, the number of updates, flashes and waveforms.

# from devloop/kindle/scenarios/aristotle-transitions.txt
label turn-fwd
tap 900 800
wait 1500
label menu-open
tap 536 60
wait 2000
/var/tmp/aristotle-observe run /var/tmp/aristotle-transitions.txt

A scenario starts from a known state (go-home) and checks its steps with snap screenshots: numbers without a look at the screen were wrong more than once. A change to what reaches the panel should keep the same updates and waveforms and stay within 10 % on latency.

Screenshots

tools/screenshots/compose.sh makes every screenshot of the README, the docs and this site from 1072 × 1448 captures of the device's framebuffer (devloop/host/screenshot.sh), kept in $ARISTOTLE_CACHE/captures/readme/. Its manifest.toml lists every output and its inputs: framed shots, and the demo's frames in the panel's 16 grays.

The demo on this site reads its frames from one file, site/demo/frames.js: each frame's image, alt text and tap targets in panel pixels. New captures or another language replace the images and that file.

Before you send a change

  • Read AGENTS.md: the framebuffer stride, the waveform numbering, one panel update at a time.
  • Run the checks in CONTRIBUTING.md.
  • Use public-domain books or text written for the test, never copyrighted books.
  • Never write to the root filesystem, boot partitions, /mnt/wfm or /var/local on a device without its owner's consent.
